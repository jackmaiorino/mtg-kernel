# CI scopes

Generated by `python tools/ci/ci_scope.py markdown` from `tools/ci/ci_scope.py`; `tools/ci/tests/test_ci_scope.py` fails if this file and the table differ.

A ready pull request whose files all map to one scope runs only that scope's checks. Files of more than one scope, a shared file, or a file no rule names run the whole pull request set. Docs files never decide. Main pushes, tags and dispatches without `scope` run the full matrix as a monitor: pushes to a line share one concurrency group (one running, one waiting, a newer merge replaces the waiting one), and a red monitor's report names every merge it covers. `ci:full` on a pull request forces the whole pull request set; labels never narrow a run. `gh workflow run ci.yml --ref REF -f scope=SCOPE` runs one scope on any ref.

## Scope to checks

| scope | ci.yml jobs | what runs |
|---|---|---|
| pr | the whole pull request set | every job of the pull request set (today's behavior) |
| trainer | rust-quality, trainer-tests | formatting and Clippy, plus the library tests of the trainer and learner modules and of what feeds a training update (TRAINER_FILTERS), Linux |
| tools | python-tools-tests | the unit suites beside the tool directories in TOOLS_DIRS (no Rust binary), Linux |
| w5-tools | none | nothing in ci.yml: w5-tools.yml runs its Linux (Python 3.11) and Windows unit jobs and the cgroup acceptance on these paths |
| python | python-env-build, python-tests | the Python test binaries and shards, Linux and Windows |
| rules-limited | rust-quality, limited-build, rust-limited-groups | formatting and Clippy, the shared Limited build and every Limited group, Linux (only Limited process binaries map here; Limited library code is engine code) |
| workflow | none | nothing in ci.yml: the changed workflow runs itself on its own paths |
| docs | none | nothing |

## Trainer scope

Library test filters: `expanded_deck_training_v1::`, `native_policy_train_step_v1::`, `native_expanded_training_run_v1::`, `native_policy_value_net_v1::`, `training_math_v1::`, `native_flat_tensorizer_v`, `inference_cache_v1::`, `native_train_state_payload_v1::`, `native_trainer_schedule_v`, `native_trainer_v1::`, `native_training_`, `native_checkpoint_`, `native_baseline_checkpoint_chain_v4::`, `fast_sampler::`, `unclamped_softmax_sampler_v1::`, `s_transformer_v1::`.

They run as 2 jobs: shard 0: `expanded_deck_training_v1::`, `native_policy_train_step_v1::`, `native_expanded_training_run_v1::`; shard 1: `native_policy_value_net_v1::`, `training_math_v1::`, `native_flat_tensorizer_v`, `inference_cache_v1::`, `native_train_state_payload_v1::`, `native_trainer_schedule_v`, `native_trainer_v1::`, `native_training_`, `native_checkpoint_`, `native_baseline_checkpoint_chain_v4::`, `fast_sampler::`, `unclamped_softmax_sampler_v1::`, `s_transformer_v1::`.

Trainer scope: CI runs formatting, Clippy and the trainer library tests only (a local run covers formatting, workspace Clippy and the library tests; the feature Clippy runs stay in the hosted rust-quality job). The bit-identity rows go with every trainer change and run on a node, not in CI: the 10-game main-chain recipe; the 60-game recipe; the pilot recipe with mulligans; the pilot recipe with mulligans and priority windows, on the znver5 build and on the portable build, and on native arm64 when Mac arms use that build. A trainer pull request without those rows linked is not mergeable under the merge rule, whatever CI says.

## Rules and cards

Engine rules and card changes that alter play are never bit-identical by scope: they run the rules groups (the whole set, or rules-limited), and, if a running lineage's trainer would pick them up, need a declaration.
