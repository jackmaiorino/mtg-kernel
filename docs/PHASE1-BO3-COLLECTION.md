# Phase 1 actual BO3 collection V1

This opt-in collector runs real engine matches and records actor-visible decisions for the versioned Phase 1 trajectory. It does not update a model, change the existing BO1 objective, launch a campaign, or establish playing strength.

The public API is `phase1_bo3_collection_v1::collect_bo3_trajectory_v1`. The command `phase1_bo3_collect_v1 --request request.json --output new-result.json` runs exactly one explicitly requested match. Its request contains `config` (`Bo3CollectionConfigV1`) and `packages` (two `CompleteAgentPackageV1` descriptors). Configuration specifies the seed, initial chooser, exact executable 60/15 registrations, labels, summary tag sets, physical-game and episode limits, and aggregate decision-record limits. The schemas are `mtg-kernel-bo3-collection-config/v1` and `mtg-kernel-bo3-collection-result/v1`.

| Component | Executed behavior | Recorded behavior probability |
| --- | --- | --- |
| Gameplay | Each acting seat's actual frozen V3 native model and existing sampler | Exact Hamilton Q64 masses from the logits actually sampled |
| Play/draw | The chooser package's fixed Play or Draw | One for the selected fixed choice |
| Opening | Existing KeepSevenV2, both seats keep seven | One for Keep; explicitly untrained mulligans |
| Sideboard | Keep, or the package's verified frozen greedy sideboard head | One for Done or the actual greedy selection |
| Search | Disabled | No search decisions or search-strength claim |

Learned London, learned play/draw, and search descriptors are rejected before gameplay. There is no fallback that silently substitutes Keep or disables an advertised component. The two packages must use the same exact runtime descriptor. Each package loader verifies its source/checkpoint and installed model identity, current executable bytes, clean compiled source tree, toolchain, card registry, feature contracts, and any sideboard head binding. A binary compiled from a dirty worktree cannot pass the public current-runtime check. Package identity includes machine-specific paths; moving files or using another interface requires another exact package, even when model content is unchanged.

## Actual visibility and behavior

The existing private `PairedBo1PolicyInputV1` remains the gameplay policy boundary. Its new crate-only recording method captures the trusted V6 observation and ordered actions from the same decision binding used for scoring. It exposes no session getter. The frozen scorer now returns its selected index and scored logits through a narrow shared helper; its original arithmetic, action ordering, and per-seat RNG consumption are preserved. The recorder reapportions those logits with the actual wide Hamilton implementation. It never samples a second action and never substitutes softmax probabilities for the actual sampling distribution.

Both real opening hands are projected separately from the same `HumanOpeningV1`. The existing protocol automatically keeps P1, then explicitly keeps P0. The first record therefore has `opponent_has_kept = false`; P0's later record has it set to true. Each record contains only that actor's own hand, public hand count, starting player, and own configuration. These fixed keeps are not learned opening decisions.

The existing summary runner owns the privileged completed-game fold. Raw summaries remain coordinator-private. Between games, the collector uses `project_sideboard_input_v1` to provide each seat only its own card outcomes and registration, publicly visible opponent evidence, and completed-game resource summaries. Tags affecting this projection are explicit configuration data and preserved in the result. No environment seed or opposite registration is passed to a policy. Match metadata, both registrations/packages, seeds, outcomes, and diagnostics are coordinator data; never feed the complete result or trajectory to a model.

The current sideboard configuration is reconstructed from the trajectory's initial registration and selected actions. Each intermediate legal action list is recorded, and the existing trajectory validator replays it. Game 3 begins with the configuration submitted in game 2. For a greedy head, the complete deliberation and every selected action can be reproduced from this history, recorded actor input, and the package's frozen head/embeddings. The scorer's internal softmax is not the behavior distribution of its deterministic argmax. Keep remains labeled Keep.

## Commit, terminal, and credit boundaries

Decision indices are contiguous across both seats, openings, sideboarding, and all physical games. A gameplay selection is held pending until the next callback confirms that the previous step returned successfully, or the existing runner returns a successful natural summary. Only then is it appended to the committed trajectory.

On any runner error, a pending selection is discarded even if the observed engine counter advanced. This includes the final successful step before a cap, because the existing runner exposes no separate successful-step receipt to the recorder. The loss is explicit in `discarded_pending_selections`. A selection rejected by the record-size/count bound is also counted there. Incomplete-game diagnostics preserve the actual observed terminal and error, but the validated trajectory leaves that game's terminal absent. It never assigns an uncertain action to the committed prefix or treats a cap/error as a natural result. Known earlier natural games remain in the trajectory.

The trajectory is validated against the exact behavior packages before returning. First-to-two match state advances only from actual successful natural game summaries. Physical draws follow the existing match state and may require additional games within the explicit limit. `match_return_v1` returns +1/-1 only for naturally complete matches. Incomplete matches have no match target and receive no weights from `equal_match_weights_v1`. The existing helper gives each complete eligible match equal total weight, irrespective of whether it took two or three games; only the selected learner seat/component receives weights. This collector does not yet implement a BO3 loss, gradient, alternating policy block, or optimizer continuation.

## Bounds, publication, and recovery limits

The collector enforces positive episode limits, 3 to 254 permitted physical games, at most 100,000 committed decision records, and at most 256 MiB summed canonical decision JSON. Reserving one game-counter value avoids overflow when recording a final permitted draw. It checks recording capacity before submitting the next recorded action. Exceeding either recording limit produces a validated incomplete prefix. The JSON-byte limit is not a resident-memory guarantee: Rust values, native models, raw summaries, pending serialization, and the final JSON buffer consume additional memory. Host-level reserves and measured worker limits remain the execution supervisor's responsibility. This implementation has no throughput qualification or acceleration claim.

The CLI reads a strict JSON request bounded to 4 MiB and refuses an existing output or staging file before collection. It publishes one immutable result through the existing synced, checked, no-overwrite publication primitive. The output parent must already exist and be exclusively owned by this run. Existing publication filesystem and Windows directory-durability limitations apply. The trajectory hash is SHA-256 of its canonical serde JSON, with no wall-clock field. The result also preserves the request configuration, exact packages, current-runtime verification receipts, seed per constructed game, and terminal/error diagnostics.

Recovery is deterministic whole-match replay from the preserved configuration/packages/seed into a new output name, followed by hash comparison. Mid-game state/RNG snapshots, partial-match append recovery, incremental crash export, and automatic process-loss recovery are not implemented. A killed process before publication may lose the in-memory match. No missing or interrupted match may be turned into a complete learning target.

## Verification and review

Source tests in `phase1_bo3_collection_v1` use actual native fixture models and legal all-basic registrations whose natural terminals are produced by engine decking. They cover two- and three-game outcomes, byte-identical whole-match replay, exact old-runner observation/action/seed parity, seat-specific opening visibility, Q64 distributions, equal match weights, incomplete exclusion, actual invalid/stale engine-step handling with unchanged or incremented counters, and record bounds. A zero-score frozen sideboard head makes actual 15-card greedy exchanges in games 2 and 3; every intermediate action/probability is reproduced from the recorded trajectory and frozen head. This head is an untrained engineering fixture.

The original generic-model all-land fixtures hit the 256 MiB recording bound in game one. Those failed results remain preserved. The corrected fixtures use explicitly engineered native weights that give Pass a finite logit below 16 and retain the exact Hamilton sampler, legal actions, full registrations and natural engine terminals. A short actual-action sanity check verifies the feature route and sampling probability before full collection. This controls fixture size without overriding actions, winners or production bounds. Long-game recording capacity remains a limitation to measure for real packages.

The engine tests call the private loaded-components boundary with explicit test-only file metadata and actual native models. They do not claim current-runtime verification for fake files.
