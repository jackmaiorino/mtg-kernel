# Pauper meta card coverage and sideboarding: design v1

Date: 2026-09-09. Author: LEAD (Fable). Status: DRAFT for Codex adversarial review and Jack's rulings (section 9). Branch: `lead/pauper-meta-cards-v1` (from the main tree head 75406ffe). Nothing here changes a training run, a pre-registered constant, or the main tree.

## 1. Goal

Jack (2026-09-09): "work towards implementing more cards into the kernel and potentially planning out sideboarding. use mtggoldfish or other sources to prioritize pauper meta relevant cards."

Two outcomes:
1. The kernel represents and simulates the cards League opponents actually play, in meta-share order, so that (a) the MTGO visible scorer stops abstaining on unknown names and (b) a later training cycle can include those decks.
2. Sideboarding exists end to end for the registered decks: a real per-matchup plan table behind the existing deterministic policy, an archetype classifier for MTGO where the opponent's deck id is hidden, the roadmap's best-of-three gate, and the reserved slot for a trained sideboard head.

## 3. Constraints that shape the design

- Registry membership requires deck membership: `build.rs` fails a card with an empty `decks` list, so every new card enters through a pool deck (a refreshed pinned deck or a new deck).
- The pool is bound to XMage: `data/pauper_pool_v1.json` pins the SHA-256 of `DeterminizationSampler.pauperDefaults()` in the Mage fork's AIRL plugin and its `.dek` files. Adding or refreshing a deck changes that Java method or a deck file, requires a Mage-fork commit (worktree `mage-cycle4-lead`, branch under the lead), and re-pins the manifest. The CP7 shadow harness reads the same decks.
- Card programs are Rust: metadata comes from `data/cards_v1.json` (cost, types, mechanics tags, XMage `java_file`), simple programs are generated by `build.rs` from the tags, and everything else is hand-written `EffectOp` programs, trigger tables, and target specs in `card_def.rs`, `effect.rs`, `engine.rs`, `trigger.rs`, with a per-wave integration test file. New card work "should compose these generic shapes and may not add card-specific pending state" (ROADMAP line 175).
- Every wave moves `KERNEL_CARDDB_HASH`, the Flat V2 goldens, and the contract digests. The branch is a card lane; landing on the main tree happens at a campaign boundary under an owner ruling, exactly as the MTGO deployment branch (design MTGO_LEAGUE_INTEGRATION_RESUMPTION_V1 section 6.1). The MTGO deployment branch may merge the card lane earlier because it already carries its own identity.
- XMage-absent cards cannot be shadow-validated. The pinned Mage fork (72a08a3b, 2026-09-02) lacks the Teenage Mutant Ninja Turtles set cards Giant's Boulder, Utrom Monitor, Leonardo Big Brother, Sewer-veillance Cam, Call Damage Control, and Elite Interceptor. They are deferred to a wave that follows an XMage refresh; until then Affinity and White Weenie coverage stop short of those cards and the MTGO unknown-card policy handles them (fail closed, human takeover).
- The model's card vocabulary is a fixed 65,537-token table (`CARD_VOCAB_SIZE_V1`), so new registry ids need no architecture change, but their embedding rows are untrained until a training cycle includes the new decks. Representation lands now; competence follows training, which is a science-lane decision (section 9).

## 4. Options

A. Drift refresh only: update the nine pinned decks to their current lists and add the roughly 25 cards that complete them. Cheapest; raises coverage of 77 percent of the field to near 100 percent; adds no archetype the model has never seen.

B. Staged meta expansion (recommended): option A as wave 1, then new pool decks in meta order (Urzatron, Gruul, White Weenie, Ephemerate, Garden), each wave a reviewed, testable increment with its own deck file, sampler entry, and manifests. Coverage of the sampled field rises from 61 percent of copies to about 97 percent, minus the XMage-absent cards.

C. Representation without decks: implement cards with no pool membership. Blocked by the deck-membership rule; relaxing it would let unplayed cards into the registry unvalidated. Rejected.

Per-wave procedure (one plan document per wave, subagent-driven, Codex review before the wave commit is called done):
1. Deck source: write or refresh the `.dek` under `oracle/xmage/decks/Pauper`, mirror it in the Mage fork's AIRL deck directory and `pauperDefaults()`, commit the Mage fork on a lead branch, and re-pin `java_factory_*_sha256`.
2. Registry: add `cards_v1.json` entries derived from the XMage Java source (cost, types, subtypes, power, toughness, mana production, mechanics tags, `java_file`), with `engine_capability` full only when the program exists.
3. Programs: prefer `build.rs` tag-generated programs; hand-write `EffectOp` programs, triggers, and target specs for the rest, composing existing generic shapes; no card-specific pending state.
4. Tests: one integration test file per wave covering each card's rules text, plus the existing goldens and manifests regenerated (`generate_pauper_manifests.py`, `generate_flat_policy_v1_goldens.py`, `generate_flat_policy_v2_goldens.py`) and the Python manifest tests updated with the new counts.
5. Shadow check: a CP7 shadow smoke of the new deck against one existing deck through the XMage harness, so the kernel and XMage agree on every new card in play.
6. Record: old and new `KERNEL_CARDDB_HASH`, pool counts, and deck hashes in the commit body.

## 6. Sideboarding

6.1 Plan table. Author `pauper_sideboard_policy_v1` plans for every ordered pair of registered decks (nine decks now, 72 ordered pairs; grows with each wave) as explicit cards-in and cards-out lists, derived from the sampled lists' sideboards and the opponent's archetype class (aggro, control, combo, artifact, graveyard). Each plan is validated by the existing `SideboardPlanV1` rules (equal counts, legal 60 and 15). Plans are disclosed constants; Jack ratifies the table before any Bo3 measurement or League use (section 9).

6.2 MTGO archetype classifier. The policy is keyed by opponent deck id, which MTGO hides. Add a deterministic classifier over visible opponent card names observed in game one: a registered-card signature table (each pool deck's distinctive cards) scores the observed names; the best-scoring registered deck above a fixed margin selects the plan, otherwise the unchanged plan. It plugs into the MTGO sideboard slot behind the same trait as today's placeholder and reports its inferred archetype and margin in every receipt. Unknown opponents keep the current behavior.

6.3 Bo3 gate (ROADMAP "Deferred sideboard and BO3 gate"): with the plan table in place, run post-board goldens and reference replays for graveyard hate, color hosers, artifact hate, sweepers, and alternate win lines; then the sampled-primary and greedy-secondary post-board matrices with BO1's failure rules. This is measurement, not tuning: the table is frozen before the matrices run.

6.4 Trained sideboard head. Reserved behind the existing `MtgoCompetitiveNativeSideboardScorerV1` slot. Its training would be Bo3 self-play over the registered 75s with terminal match win-loss as the only reward; whether and when to spend a training cycle on it is a science-lane decision and is not part of this design.

## 8. Risks

- Each wave changes the pool identity and the card DB hash; a landing mid-campaign would break contract digests, so the lane stays unmerged until the boundary.
- Hand-written programs for the complex cards (Utopia Sprawl, Ram Through, Campfire, Delver of Secrets, Glint Hawk) can diverge from XMage; the per-wave shadow smoke exists to catch that before the wave is called done.
- The sampled window is two weeks; archetype shares move. The ranking is regenerated from the JSON, so a re-run before each wave is cheap.
- Refreshing pinned decks changes the CP7 anchor decks' contents; anchors are measurement-only and their identity is recorded by hash, but a refreshed Burn list is a different opponent than the historical one. Historical results keep their recorded deck hashes; new measurements state theirs.
