Open questions raised by the designers:
- What per-game wall-clock does the current checkpoint actually run at (needed to size N and the section 2/4/8 compute budget with real numbers instead of a formula)? Requires the W2 calibration run this design assumes but does not execute.
- What are the exact operational definitions of 'removal with no target' and 'counterspell held' as event_history reconstructions? I proposed heuristics (a targeted removal spell resolving with its target still on the battlefield untouched; an instant-speed counterspell held in hand through an untapped mana source at end of turn) but these need ratification before the extractor schema freezes.
- Does the search campaign (section 4) need the same BO1-acceptance sequencing exception the existing pauper-meta-cards design requires before any Bo3 measurement (its section 6.4), given it produces win-rate claims about the current checkpoint on candidate 60s?
- Should the paired estimator use per-game (Bo1) or per-match (Bo3) win outcomes as the unit for the bootstrap, given the existing design's 6.4 already commits to matches as the match-win claim unit but this harness could run either?
- What is the acceptable false-accept rate (alpha) and per-cell N tradeoff given the RunPod credit budget, and should N scale with the observed effect size class (mainboard swap vs full sideboard plan) rather than being one fixed number across all 81 pairs?
- Should postboard catalog entries (section 5, W6) be versioned per accepted-table revision, so a later search update does not silently change what a previously-scheduled self-play run trains against?
- What is the measured per-decision forward-pass latency and per-candidate wall-clock cost on the current checkpoint? Section 2, 4, and 8 sizing and the section-4 search budget depend on this number, which needs to be measured, not assumed.
- Should the eval harness's terminal-only episode runner also be wired to optionally emit a lighter, non-digest-chained trajectory-shaped record for debugging, or should it stay strictly minimal with only win/loss and the GameSummaryV1 row?
- What exact per-card role tags (removal, counterspell, and any others needed for own_card_outcomes) are required, and who curates and validates that offline table against cards_v1.json's mechanics tags?
- Does the RL refinement stage need its own frozen opponent pool (the nine registered decks, or the post-board catalog from section 5) held fixed during training, or should the opponent distribution itself be a tunable choice the owner rules on?
- Should the search procedure's coordinate-ascent neighborhood also consider multi-slot correlated swaps (a themed multi-card exchange) beyond single card-pair mutations, given the drafted warm start already reasons about multi-card packages?
- For the MTGO slot, what history depth N (number of prior completed games or matches) should the deck model condition on, and does that differ between the kernel self-play training distribution and live MTGO matches where history is scarcer?
- What are the pre-registered acceptance margin m and per-cell sample size N for the sideboard search procedure (Section 4), and the opponent-field weighting for the win-rate estimator (Section 2)?
- Which training cycle boundary absorbs the new runtime_decks_v1.json rows once sideboard plans are frozen, and who owns authoring/reviewing the fixed requires-target and is-counterspell card-metadata tables the extractor depends on?
- Should deck model v1's promotion bar be strict non-inferiority to the frozen search table or a required improvement margin, and is PPO with a sparse win-rate-delta reward (computed from a batch of eval-harness games per episode) an acceptable RL refinement design, or does the owner want a different refinement objective given its variance risk?
- Is a new RL session schema version (V7) for arbitrary-deck evaluation acceptable under the frozen-protocol discipline, or does the owner want the eval harness built as an entirely separate binary/entry point that never touches rl_session.rs's wire types at all?
- What is the exact classification rule (static card-definition tags) for removal_with_no_target and counterspell_held in the game-summary extractor? These outcome fields need an intent label that does not currently exist on card definitions.
- What is the pre-registered acceptance margin for the sideboard-table search (how much better than the incumbent, in win-rate CI terms, counts as a genuine improvement vs. noise)?
- What sampling fraction of self-play episodes should reset from post-board configurations once section 5 lands, and is this worth a training cycle now versus later, given it competes with other science-lane priorities?
- Should RL refinement of the deck model (section 6) be funded in the near term, or should v1 ship to MTGO as imitation-only against the search table, deferring RL to a later cycle?
- What confidence or evidence-coverage threshold should gate flipping the MTGO slot's qualified_for_live from false to true, given the checked-untrusted response validation already in competitive_auxiliary_model_scoring.rs is necessary but not sufficient?
- Should Unknown-opponent behavior for the deck model diverge from today's classifier fallback (e.g., a learned generic-opponent board plan) or stay identical (submit unchanged) for v1?
- How should the search procedure's branching factor and neighborhood radius (section 4) be sized against the not-yet-measured per-candidate cost from section 2, without presupposing a compute budget the owner has not set?
