# Deck model: sideboarding now, brewing later: design v1

Date: 2026-09-09. Author: LEAD (Fable) with a four-design judge panel. Status: DRAFT for Codex review and Jack's rulings.

## 1. Goal and claims kept separate

Goal: the shortest verified path to data-driven, disclosed sideboard tables for MTGO Leagues using the current frozen checkpoint, then a separate deck model that amortizes and refines that table. This document starts from the judge panel's winning design (key: harness-first, winner in two of three verdicts) and grafts the strongest verified ideas from the other three (learning-first, data-contract-first, deployment-first), closing every fatal flaw a judge listed against any of the four. No training happens in sections 2 to 4. The deck model (section 6) is later work, gated by an owner ruling, not a prerequisite for usable tables.

Six claims stay separate and are never conflated in a report:

1. Representation: a card has a validated program in `data/cards_v1.json` / `card_def.rs` (generated by `build.rs`; module doc confirms `CARD_DEFS` and `card_id_by_name` are both codegen'd from that file, `src/card_def.rs:1-5`).
2. Post-board rule validity: a plan's `cards_in`/`cards_out` conserve the registered 75 and produce a legal 60 plus 15 (`SideboardPlanV1`, `src/sideboard.rs:297`).
3. Playing competence of the current checkpoint on a given 60, measured by the harness (section 2): checkpoint-relative, and for any configuration touching the 15-card sideboards also untrained-embedding-relative. Those cards are registered in `data/pauper_pool_v1.json` but never played in self-play, so their rows in the shared 65,537-entry card-embedding table (`CARD_VOCAB_SIZE_V1`, `src/native_policy_value_net_v1.rs:69`) are untrained. A harness number on a sideboard-heavy 60 measures the checkpoint's competence with weak representations, not the card's true value.
4. Search-table validity: a table is warranted only for the checkpoint that generated it (weights hash plus git HEAD). A new checkpoint invalidates prior tables as ground truth; they remain a warm start only.
5. Deck-model competence (section 6): imitation fidelity against the frozen table and RL win rate are different numbers, reported separately, never assumed to agree.
6. MTGO transfer: deployment competence on strictly visible-only evidence is measured separately from full-information self-play win rate, and inherits claim 3's embedding caveat.

Existing ratified constraint this design sits inside: Jack's 2026-09-09 sequencing exception (`docs/superpowers/specs/2026-09-09-pauper-meta-cards-and-sideboarding-design.md:149`, "exception granted... nothing measured under this exception is reported as a 'Pauper match' or BO3 promotion result") lets sideboard-plan authoring and Bo3-shaped measurement proceed ahead of the sampled-primary BO1 matrix, but does not on its face cover this document's new search campaign or deck-model claims. Whether it extends to them is an open owner ruling (section 10).

## 2. Evaluation harness

Interface: `resolve_runtime_decks` (`src/rl_session.rs:6992`) resolves only `SessionDeckIdsV1` strings (`[String; 2]`, `rl_session.rs:50`) against the build-time `RUNTIME_DECKS` catalog (`runtime_deck_by_id`, `src/runtime_decks.rs:29`). The function it feeds, `build_session_deck_pair_state` (`rl_session.rs:6914`), dispatches to `build_deck_pair_state` / `build_deck_pair_state_with_starting_player_v1` / `build_deck_pair_state_environment_v2` / `build_deck_pair_state_environment_v2_with_starting_player_v1` (`src/rl.rs:1345, 1362, 1429, 1449`), all confirmed to already take plain `&[u16]` slices, not `'static` catalog references. `flat_policy_v2.rs` encodes off the resulting `GameState`, never off a deck id, so it is untouched by anything below.

Change (file: `src/rl_session.rs`): add `resolve_explicit_decks(mainboards: &[Vec<u16>; 2]) -> Result<[Vec<u16>; 2], RlSessionError>` beside `resolve_runtime_decks`. It checks each list has exactly `REGISTERED_MAINBOARD_SIZE_V1` (60, `src/sideboard.rs:15`) entries before anything else, then runs `card_def::preflight_fully_supported_deck` (`src/card_def.rs:1344`, already used at catalog build time), no catalog lookup. Add `RlEpisodeSessionV1::reset_with_explicit_decks_and_limits` and a `FastActorSessionV1` sibling, mirroring `reset_with_decks_and_limits` at `rl_session.rs:3961` and `rl_session.rs:4633` respectively, calling `build_session_deck_pair_state`'s inner builders directly with the explicit lists in place of `resolve_runtime_decks`. `SessionDeckHashesV1` (`[u64; 2]`, `rl_session.rs:51`) for an explicit deck is computed with the catalog's own algorithm, `"fnv1a64-serde-json-u16-array/v1"` (`build.rs:1954`, hashed at `build.rs:2202-2205`, `fn fnv1a64` at `build.rs:6912`), so a table entry later promoted into `RUNTIME_DECKS` (section 5) hashes identically.

Candidate source: `checked_in_pauper_registered_deck_by_id_v1` plus `RegisteredDeckV1::apply_plan_v1` (`src/sideboard.rs:229, 152`) turn a `SideboardPlanV1` into `DeckConfigurationV1::mainboard()` (`sideboard.rs:68`), a `Vec<u16>`. The harness takes `(self_deck_id, opponent_deck_id, game_index, cards_in, cards_out)`, materializes the candidate 60 for one seat and the opponent's registered mainboard for the other, feeds both to the new resolver.

Paired seeds: for a fixed opponent, run N paired episodes per candidate against the incumbent plan, reusing the existing `EnvironmentV2` seed pairing (`ResetRandomization::EnvironmentV2 { pair_environment_seed }`, `rl_session.rs`) so candidate and incumbent share identical shuffles and play/draw sequence, canceling shared randomness in the paired difference.

Estimator: per seed, `delta_i = win(candidate) - win(incumbent)` in `{-1, 0, 1}`; report mean delta with a paired-bootstrap confidence interval, matching the existing design's committed unit for match-win claims (`pauper-meta-cards-and-sideboarding-design.md:114`). BO1 games are the unit for search iteration (cheap, high iteration count); BO3 matches through `BestOfThreeDeckMatchV1::prepare_game_v1` (`src/bo3_session.rs:45, 100`) are the unit for ratification-grade measurement, since game-index 2/3 evaluation needs that path regardless. N is fixed and pre-registered before any candidate is scored; no peeking, no early stop on a favorable trend.

Cost: one calibration run measures real per-game wall clock under the frozen checkpoint before any campaign-wide N is set; this number feeds sections 4 and 8's budgets rather than an assumed figure.

## 3. Game-summary extractor

Source: `state.engine.event_history: Vec<CommittedEvent>` (`src/engine.rs:155`), whose own doc comment calls it the full permanent record of every committed event this game, in commit order, never drained. No variant carries a turn stamp, confirmed across `Damage`, `ZoneChange{object, from, to, controller_before}`, `LifeLoss`, `LifeGain`, `Draw{player, object: Option<ObjectId>}`, `Tap`, `ManaAdded`, `CreateToken{object, token_def, controller}`, `SpellCast{spell, controller}`, `Targeted{target, target_zone_change_count, targeting_stack_item, targeting_controller}`, `CombatDamageToPlayer{source, source_zone_change_count, player, amount}` (`src/event.rs:322-410`). The extractor therefore runs in-loop (the same episode driver that steps `RlEpisodeSessionV1`/`FastActorSessionV1`, section 2), watermarking `event_history.len()` against live `GameState.turn` (`src/state.rs:1157`) at each decision boundary, then walks the full history once at episode end using a live `ObjectId -> card_def: u16` map seeded from `GameObject.card_def` (`state.rs:213`) and updated on `CreateToken`/`ZoneChange`.

Fields, per game per side:

- `opponent_evidence: Vec<{card_id: u16, first_seen_turn: u16, end_of_game_zone: enum}>`, from the first event revealing an opposing object via a public zone.
- `own_card_outcomes`, keyed by our registered-75 card ids: `{times_drawn: u8, cast: bool, stuck_in_hand: bool, died_without_dealing_damage: bool, removal_no_target: bool, counterspell_held: bool}`. The first four fold from `Draw`, `SpellCast`, end-of-episode hand contents, and a graveyard/exile `ZoneChange` with no preceding `Damage`/`CombatDamageToPlayer` from that incarnation. `removal_no_target` and `counterspell_held` need a second, live signal `event_history` cannot supply after the fact: whether the card was ever a legal cast at all. The extractor also hooks `legal_action_candidates_v5` / `core_policy_action_candidates_v5` (`src/rl.rs:1857, 1882`), the same enumeration the policy already consumes every decision, recording whether a requires-target removal spell in hand was ever offered as a legal cast this game. Combined with the post-hoc "cast but resolved with no traced target" case, this gives an operational definition for both fields instead of a pure post-hoc heuristic. The card-level requires-target/is-counterspell tag set is a small offline metadata file, ratified before the schema freezes (section 10).
- `resource_curve`: `lands_by_turn`, `hand_size_by_turn`, `life_by_turn: [Vec<i16>; 2]`, `first_attack_turn`, `damage_dealt_total`, `damage_taken_total`, folded the same way from `ZoneChange`, `Draw`, `LifeLoss`/`LifeGain`, `CombatDamageToPlayer`, indexed by the turn watermark.

Storage: a new append-only JSONL store, separate from `native_full_episode_trajectory_v2.rs`'s digest-validated training store, one row per `{episode_id, deck_ids, deck_hashes, seat, opponent_evidence, own_card_outcomes, resource_curve, winner}`, joined to a trajectory only by `episode_id`. This never touches the training store's provenance digests.

Privacy on MTGO: the schema is shared between two populators. The kernel-native one has full state access but drops anything an MTGO player's own UI would not show (library order, opponent hand). The MTGO populator, built only from `MtgoCompetitiveExternalCompletedMatchHistoryConsumerV1` (`integrations/mtgo_dxgi_capture_v1/src/competitive_native_sideboard.rs`), is a strict subset by construction, not by a separate filter: every field it can fill is already visible-card-name-keyed and player-visible, matching `MtgoCompetitiveNativeSideboardCardCountV1`'s own doc comment, "Kernel card-database IDs are deliberately absent because they are adapter metadata, not game information shown to the seated player" (`competitive_native_sideboard.rs:18-24`). A field the MTGO stream cannot fill is recorded absent, never inferred.

## 4. Search-generated sideboard tables

Procedure: for each of the 81 ordered `(self_deck_id, opponent_deck_id)` pairs and each `game_index in {2, 3}` (`SideboardPlanV1` keys on exactly these, `sideboard.rs:297, 300`), generate K candidates and score each against the incumbent with the section 2 harness at the pre-registered N.

Candidate generation: warm-start from `docs/research/sideboard_plan_inputs_2026-09/plan_table_draft_nine_v1.json`, then local search: bounded 1-to-4-card swaps, restricted to cards already present in the deck's own registered 75 so `apply_plan_v1`'s conservation rule is satisfiable by construction. Greedy hill-climbing, incumbent replaced only on acceptance, bounded by a fixed max-iteration count per cell.

Acceptance rule, pre-registered before search starts: a candidate replaces the incumbent only if the paired-bootstrap CI lower bound on mean delta exceeds 0 at a fixed one-sided alpha (0.05 default), using the full pre-declared N once. No repeated testing at partial N, no stopping early on a trend.

Freezing and disclosure (file: a new companion receipts file alongside `data/pauper_sideboard_policy_v1.json`): every evaluated candidate, accepted or rejected, is logged with its `cards_in`/`cards_out`, measured delta, CI, N, and seed list, so a rejected candidate stays auditable and rerunnable, not only the winners. An accepted plan's row plus the exact checkpoint identity (weights hash, git HEAD) is written into `data/pauper_sideboard_policy_v1.json`, committed off the launch branch. From that point the plan is a pre-registered constant: no further outcome-based tuning without a new registration and a fresh search.

Regeneration per checkpoint: a table is valid only for the checkpoint recorded in its receipt (claim 4, section 1). A new checkpoint invalidates prior tables as measurement; every prior table is retained on disk by checkpoint hash for audit, never overwritten, and remains usable only as the next search's warm start.

## 5. Training exposure

Mechanism only, not a scheduling decision. Today `RUNTIME_DECKS` (`src/runtime_decks.rs:11`) is generated by `build.rs` from `data/runtime_decks_v1.json`; sideboards in `data/pauper_pool_v1.json` are registered but never played. To expose an accepted post-board 60 (section 4's output) to self-play, add it as an ordinary named entry (file: `data/runtime_decks_v1.json`) built the same way (same `fnv1a64` convention, same `preflight_fully_supported_deck` gate), so `resolve_runtime_decks` (`rl_session.rs:6992`) needs no code change, only more catalog rows. `SessionDeckIdsV1` and the session contract are unchanged; `flat_policy_v2.rs` and `CommittedEvent` stay untouched.

This is purely additive on the training-store side too: `native_full_episode_trajectory_v2.rs`'s admission gate, `resolve_physical_deck_v2` (line 548), hard-requires `runtime_deck_by_id` resolution and rejects anything else as `InvalidDeckId` (line 553). A catalog-promoted post-board 60 satisfies this unmodified, no edit to the provenance gate itself; section 2's harness episodes, which never resolve through the catalog, correctly never enter this store at all.

Science-lane boundary: whether and when to spend a training cycle on post-board exposure, and the self-play sampling mix across mainboard/post-board pairings, is an owner ruling (section 10).

## 6. Deck model v1

Inputs: our registered 75 (card ids plus per-card outcome features from section 3), the opponent-evidence set from recent `GameSummaryV1` rows against this opponent (or Unknown), match score (`next_game_number`, `acting_player_games_won`, `opponent_games_won`), current configuration.

Architecture: the shared card-embedding table (`CARD_VOCAB_SIZE_V1 = 65,537` rows by `CARD_EMBEDDING_DIM_V1 = 16`, `src/native_policy_value_net_v1.rs:68-69`) feeds two permutation-invariant set encoders (masked mean or small attention pooling): one over the 75 registered cards, one over the variable-length opponent-evidence tuples, with an explicit Unknown-card bucket for MTGO's hidden identity. Within a Bo3 match, the 0-to-2 completed games are pooled with an explicit game-index positional feature rather than plain permutation-invariant pooling, since which game a piece of evidence came from matters: game-1 evidence predates any sideboarding, game-2 evidence postdates it. The embedding table is loaded read-only from the frozen play-model checkpoint: the deck model never writes to it, so its card representation cannot drift from the play model's own, and the two cannot co-adapt during RL refinement below. Pooled outputs concatenate with resource-curve summary statistics into one match-context vector feeding policy and value heads.

Action space, internal representation: sequential swaps keyed by card_id, with a done action, matching the vocabulary already implemented for MTGO, `MtgoCompetitiveNativeSideboardDeliberationActionV1` (`integrations/mtgo_dxgi_capture_v1/src/competitive_native_sideboard_deliberation.rs:29-32`), bounded by `MTGO_COMPETITIVE_NATIVE_SIDEBOARD_MAX_DECISIONS_V1 = 64` (same file, line 15). That enum's real fields are `MoveOneToMainboard{visible_card_name: String}` / `MoveOneToSideboard{visible_card_name: String}`, deliberately name-keyed, not id-keyed: its own doc comment states "no adapter card ID... is present" (lines 26-28), matching the Daybreak condition. The deck model's policy head therefore emits card_id logits internally, and only the MTGO slot implementation translates at the boundary, reusing code that already exists for exactly this purpose elsewhere in the MTGO integration: `card_id_by_name` (generated by `build.rs:6495` from `data/cards_v1.json`, confirmed already called at `integrations/mtgo_dxgi_capture_v1/src/actuator.rs:17827` and `competitive_auxiliary_action_resolution.rs:485`) resolves an incoming visible name to a card_id, and the reverse lookup for emitting an action is `CARD_DEFS[card_id].name` (`src/card_def.rs:934`, `CardDef.name: &'static str`). No new translation code is invented, only a call site added at the slot boundary; this closes the "no translation layer" gap a judge found in an earlier draft.

Imitation target: behavior-clone against the frozen search tables (section 4), converting each accepted plan's `cards_in`/`cards_out` into a canonical swap sequence, with the measured win-rate delta as a value-head target.

RL refinement: after imitation warm-start, refine via Bo3 self-play with terminal match win-loss as the sole reward, matching the existing design's reserved-slot framing (`pauper-meta-cards-and-sideboarding-design.md:116`), KL-regularized toward the imitation policy to bound drift off the audited table's coverage. The play-model checkpoint stays frozen throughout, for the same no-co-adaptation reason as the embedding table above.

Evaluation: identical harness and single-shot acceptance discipline as sections 2 and 4; BO1 for iteration, BO3 for the ratification-grade number (section 2); a promoted model version is itself a pre-registered constant with the same freeze and disclosure.

MTGO deployment: implements `MtgoCompetitiveNativeSideboardScorerV1` and `MtgoCompetitiveNativeSideboardDeliberationScorerV1` behind the existing slot, replacing `MtgoPlaceholderSideboardControllerV1` (`placeholder_sideboard_controller.rs`), consuming completed-match history via `MtgoCompetitiveExternalCompletedMatchHistoryConsumerV1`. Because `MtgoCompetitiveNativeSideboardModelInputV1` carries no opponent-deck-id field at all (confirmed at `competitive_native_sideboard.rs:39-43`: `next_game_number`, `acting_player_games_won`, `opponent_games_won`, `current_configuration` only), the deck model cannot and does not take a classifier-resolved opponent id as input; it conditions on visible evidence directly, so opponent-id inference and plan lookup collapse into one learned function, subsuming the archetype classifier from the existing design's sections 6.2-6.3 without also depending on that classifier's output. The placeholder's fail-closed default, submit unchanged under Unknown or low-confidence evidence, is preserved as the deck model's own fallback.

## 7. Brewing extension

Reused: the set encoder, the shared embedding table, the sequential-swap action framing (generalizes from a closed 75 to an open pool), the paired harness and evaluation protocol.

Must change: the action space widens from the registered 75 to the full pool (150 non-token cards today) and eventually beyond it. The fixed embedding table stops being sufficient once brewing must reason about cards with no self-play exposure; the untrained 15-card sideboards are the same failure mode at smaller scale (claim 3, section 1).

Prerequisite: a feature- or text-based card encoder (mana cost, types, oracle-text embedding) replacing or augmenting id lookup, so an unseen card id yields a usable vector instead of an untrained row. This is a distinct, larger workstream, explicitly out of scope for v1, matching the owner's stated build order.

## 8. Work breakdown

- W1 harness deck-injection seam (`src/rl_session.rs`), small, 0.5 to 1 day.
- W2 paired estimator plus one calibration run for real per-game cost, small, 1 day; depends on W1.
- W3 game-summary extractor including the live legal-action hook, medium, 2 to 3 days; depends on W1 for episodes.
- W4 requires-target/is-counterspell metadata tag file (offline data), small, 0.5 day; feeds W3, no code dependency.
- W5 candidate generator and search driver, medium, 2 days; depends on W1, W2.
- W6 search campaign execution and full candidate-log write, compute-bound not engineering-bound; depends on W1 to W5.
- W7 post-board catalog extension (`data/runtime_decks_v1.json`), small, 0.5 day; depends on W6's frozen output.
- W8 deck model v1: encoder, action head, imitation, RL refinement, MTGO card_id/name boundary; large, 1 to 2 weeks; depends on W3's schema and W6's imitation targets.
- W9 MTGO slot wiring and qualification, small to medium, 2 to 3 days; depends on W8 and the existing trait contract.
- Brewing (section 7): unsized, blocked on the card-representation prerequisite, independent of W1 to W9's timeline.

## 9. Risks

`event_history` has no turn stamp, coupling the extractor to the self-play driver rather than an offline replay tool (mitigated: `flat_policy_v2.rs` and `CommittedEvent` stay untouched). Search cost scales as N times 81 pairs times up to 2 game indices times K candidates; under-provisioning N inflates false-accept risk on the pre-registered CI rule, over-provisioning burns compute budget, so W2's calibration must land before committing to a campaign-wide N. MTGO opponent evidence per League match is sparse, so the deployed model may see far fewer evidence tokens than self-play summaries provide; the encoder must degrade gracefully toward the table's Unknown-opponent default. `removal_no_target` and `counterspell_held` now have an operational definition (section 3) but it still rests on a hand-authored requires-target/is-counterspell tag file; an unreviewed or drifted tag silently corrupts the field with no failing test. Terminal match win-loss is a single bit spread over a multi-hundred-decision RL episode; if this proves too sparse in practice, a batch-averaged harness win-rate delta over several matches is the fallback, but that is a deviation from the existing design's section 6.5 framing and needs its own owner ruling before use, not a silent substitution. The MTGO card_id/visible_card_name translation (section 6) depends on exact string matches between `CARD_DEFS[id].name` and the adapter's captured name; client-side aliasing, localization, or punctuation drift would silently break the mapping and needs its own validation pass before the slot goes live. Post-board catalog entries touch `build.rs` and must be sequenced outside any launch or build freeze window.
