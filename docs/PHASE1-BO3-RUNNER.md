# Finite native BO3 runner

This is an explicit CPU match-return gameplay path. `phase1_bo3_trainable_v1 run --request ABS [--max-new-batches N]` calls `run_native_bo3_training_v1`. The optional invocation limit pauses only after a completed attempted batch. Existing collect, prepare, update and ordinary BO1 ten-fresh-games interfaces keep their contracts. This implementation does not select a production number of matches per batch.

The strict `mtg-kernel-native-bo3-training-run/v1` input contains an initial complete learner package, explicit `ordinary_checkpoint_transition` or `bo3_checkpoint` input, latest `previous_progress`, exact optimizer scalar bits, fixed opponent package roster, preparation limits, collection worker count, output directory and finite ordered batches. Each batch contains 1..32 scheduled matches with an explicit collection configuration, learner seat, opponent assignment, native capture limits and `max_result_bytes`. Opponents are fixed roster entries, the initial learner, the current batch learner, or a completed earlier batch. Only gameplay is rebound; KeepSevenV2, fixed play/draw, Keep sideboarding, the sampler and disabled search stay frozen. Runtime package pins must identify the actual clean executable running this interface.

| Stage | Preserved rule |
|---|---|
| Resolve | Freeze one current learner for the entire batch; resolve both physical seats and historical opponents in schedule order. |
| Preflight | Use the existing physical-match identity to reject duplicate inputs within the batch and against consumed progress before collecting. Changing a label, cap or learner-seat annotation does not create a fresh physical sample. |
| Collect | Each match owns its policies, RNG and game state. All exact requests are saved before dispatch. Independent matches can use 1..32 workers, each with an explicit 16 MiB stack. Games within a match remain sequential. |
| Publish | Each worker serializes one bounded result, drops the captured object, saves an exact request/result hash intent, then publishes the final capture. It returns only pins and drops its byte buffer. |
| Prepare/update | Combine all attempted captures in original schedule order and call the existing updater once. Its preparation replays actual native decisions, assigns equal eligible-match weights and applies at most one Adam step. |
| NoUpdate | Preserve exact source, parameter, moment, gauge and optimizer-step bits. Advance attempted batches and matches and retain the returned progress pin. |
| Continue | Use the returned learner and latest progress for the next batch. An ordinary NoUpdate remains an ordinary transition input until a Ready operation creates the explicit BO3 checkpoint. |

The manifest and completion receipts are immutable and the run directory has an OS lifetime file lock. Resume checks a contiguous completed prefix, resolves its original packages, stream-hashes each distinct payload once, and checks compact saved progress against the original native DTO. The first prefix edge is anchored to the initial declared progress and all subsequent counters advance by exactly one attempted batch. Full model/optimizer validation is performed at the reconstructed latest tip, without deserializing every historical checkpoint tensor set. Progressive ledgers still incur growing metadata I/O; this is reported rather than hidden.

For an interrupted collection, an intent without its final result is an incomplete execution attempt. Preserve it and recollect the same request/seed in a fresh attempt directory on the next invocation. A final result must have its prior intent and exact request binding and must hash correctly. A corrupt or conflicting final file fails the invocation. Valid incomplete matches remain attempted evidence and are never backfilled to achieve a completion quota. Collection errors, serialization overflow or panic stop new assignment, join all active collectors and prevent update. This is dispatch cancellation, not cooperative engine cancellation. The outer process lifetime cap handles a hung engine.

For an interrupted update, a published checkpoint or progress is given to the existing updater with the exact original request. Its checkpoint-only recovery publishes missing completion without calling Adam. If neither checkpoint nor progress was committed, preserve the incomplete operation and use a fresh operation directory with the same parent and preparation on a later invocation. The runner does not automatically retry errors within an invocation. Operation `optimizer_updated` records that operation's disposition; recovery does not imply another optimizer call.

Resource bounds are explicit: 16 MiB run manifests, 4 MiB individual collect requests, 1 MiB preparation/update requests, at most 4,096 batches and 65,536 cumulative attempted matches including prior progress, and the existing 512 MiB preparation-input and 256 MiB prepared-native-payload limits. Known result-cap sums are checked for every planned batch before any collection. Each resolved batch also checks the sum of exact request bytes plus declared result serialization caps against its preparation-input limit. No full-batch capture objects or JSON trees are accumulated. These byte and stack bounds are not an aggregate RSS guarantee. Policy/engine allocations, allocator overhead, process RAM/disk reserves, eligible CPU quota, financial budgets and termination remain the outer supervisor's responsibilities.

Timing is outside immutable training inputs. Per-invocation and batch telemetry records requested/started workers, busy wall seconds, reused/completed/failed slots, preserved interrupted execution attempts, collection including recovery/publication, and combined preparation/update/checkpoint/readback time. Those latter stages are not separately exposed by the current update API. CPU activity, GPU activity, spend and useful speedup must come from the execution supervisor and measured work; worker count is not a utilization or acceleration result.

The new source checks cover ordered worker results, cancellation/join behavior, prefix gaps and NoUpdate counter separation, strict parsing/bounds, and intent-before-payload publication with preserved corruption/partial files. They do not fabricate a clean runtime or establish native game parity. Root must still run the real clean-executable schedule with both learner seats, a multi-match batch, ordinary NoUpdate followed by fresh Ready work, subsequent BO3 continuation, serial/parallel comparison, pause/resume and actual process interruption. Compare full state bits and capture semantics under an explicitly documented path/provenance normalization, not arbitrary field stripping. No playing-strength, auxiliary-policy benefit, new independent lineage, GPU numerical envelope, cloud acceleration or human competence follows from these engineering checks.
