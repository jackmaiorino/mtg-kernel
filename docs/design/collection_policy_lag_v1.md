# collection_policy_lag_v1: a lag-1 collection recipe (design)

Notation: θ_j is the full train state (parameters, Adam moments, step) at global update boundary j; θ_0 is a chain's start or fork state; update j consumes batch j and maps θ_j to θ_{j+1}. β_j is the state batch j is played on. Run-config key `collection_policy_lag_v1`: absent or 0 is today's recipe and is never serialized; 1 is this recipe. It changes what is learned, so no chain may use it before a signed declaration.

## 1. Which parameters each batch sees, and where it is recorded

- Today β_j = θ_j. Under the flag β_0 = θ_0 and β_j = θ_{j-1} for j ≥ 1: batches 0 and 1 both play θ_0, and batch j+1 (on θ_j) is collected while update j runs. A `current` opponent is β_j (self-play stays self-play); a `completed_iteration` opponent must be at least two iterations old, refused at config validation otherwise.
- Fresh start: β_0 is the initial source. Resume inside a run (a crash anywhere): β_j is read from committed receipts (iteration j-1's `source`), never from what a process held, so a resumed run computes the same β_j.
- Segment boundary: segment length is an implementation choice (256, 16, 64), so the recipe must not depend on it and the lag carries across. A continuation config names `collection_policy_lag_carry_v1`, the source the previous segment's last update started from; the run refuses it unless its initial checkpoint records exactly that source and state as its update input. A segmented chain is bit-identical to an unsegmented one.
- Fork: no carry, so β_0 is the fork state (no lag on the first batch); the fork lags from its batch 1 on.
- Stop at a declared update k (iteration limit, chain ledger, end of the schedule): the committed state is θ_{k+1}, whose checkpoint names θ_k, and the run result names θ_k as `collection_policy_lag_next_behaviour_v1` (the carry of a continuation). An iteration-limit stop starts no next collection; after a ledger stop a finished next collection is an ordinary attempt of iteration k+1, reused by a relaunch because it is the batch the uninterrupted run plays.
- Records (all absent without the flag): `collection.json` and every trajectory already record what they played (`source`, `behavior_state_sha256` = β_j). `update.json` and `complete.json` add `collection_policy_lag_v1: {lag, behaviour, behaviour_state_sha256}` (`source`, `before_state_sha256` stay θ_j). Each checkpoint a lag update writes adds `{lag, input, input_state_sha256, behaviour, behaviour_state_sha256}`. `run.json` and the result add `collection_policy_lag_v1: 1`.

## 2. The learner

What the update assumes: the behaviour policy of every learner row is the update's own input. It refuses a trajectory whose behaviour state hash is not its source's ("stale trajectory"), replays every row of both seats against the bound behaviour policies (`ordered_update_preparation`, `validate_actual_behaviors_v1`), and the GAE step recomputes each learner row's forward tape at its own parameters and refuses any bit that differs from the stored logits and value (`validate_forward_output_bits_v1`). The loss (`gae_v1.rs`) is (1/G) Σ_g [-A_g Σ_s log softmax(z_gs)[a_gs] + c (V(x_g) - y_g)^2], with A, y from GAE(γ, λ) over the stored values and A normalized per update; the entropy coefficient is fixed at 0. There is no ratio and no clipping: the stored logits (the behaviour log-probabilities) serve only as the bit check. So the update is exactly on-policy A2C, and the stored log-probabilities do not make it correct under a lag. With the gradient taken at θ_j for a batch played on θ_{j-1}, the bit check refuses every lagged row; without the check the gradient is a biased off-policy estimate, and correcting it needs per-row ratios π_θj/π_θj-1 (joint over substeps), clipping or truncation, and V-trace targets: a loss change, not taken.

Chosen design, no loss change: evaluate the unchanged loss, forward, bit check and backward at β_j, the parameters that played the batch, and apply that gradient through Adam to θ_j with θ_j's moments and step: θ_{j+1} = Adam(θ_j, m_j, v_j; ∇L_j(β_j)). Every gradient is an exact on-policy gradient (the bit check now proves the gradient point is the behaviour policy); it is applied one update late, which is delayed-gradient SGD with staleness 1. When β_j = θ_j (the first batch after a start or a fork) the update is bit-identical to today's. It is still a recipe change (the step no longer follows the gradient of the point it moves from), but it adds no term, coefficient or hyperparameter. Scope: the plain CPU GAE update (sequential or fixed-partition backward, either training math, the London and pass offsets); refused with CUDA, line (b), E, SQ1, search targets, EX1, an S learner, registry transfer, the terminal or recovery loss, and the exact GPU learner.

## 3. Resume, checkpoints and the replay check

The chain state at boundary j is the pair (θ_{j-1}, θ_j). A checkpoint carries a reference, not the lagged parameters: the source and state hash of its update's input, which is the next batch's behaviour; those parameters stay in their own checkpoint file and are verified by pin and state hash when loaded. After a crash at any publication a resumed run recomputes β_j from receipts and reuses only fully published phases: a next-batch collection is an attempt of iteration j+1, reused only if its `collection.json` validates against β_{j+1}, restarted otherwise. The replay check moves with the behaviour: the update loads β_j, binds every trajectory to β_j's state, replays every row and differentiates at β_j, and refuses a behaviour that is neither its own source nor the input recorded in its source checkpoint (lag exactly one, along the actual lineage). Outside the trainer (not in this patch): retention must keep θ_{j-1} while θ_j is a resume or replay point, and the chain driver and replay configs must pass the carry.

## 4. Rate and memory

Per update today c + u + o; lag-1 steady state max(c, u) + o (the update, its validation and receipt overlap the next collection; collection validation stays serial).

| games/update | today | lag-1 | speed-up | bound (o hidden) |
|---|---|---|---|---|
| 60 (c 0.343, u 0.208, o 0.080 s) | 0.631 s, 1.58 updates/s | 0.423 s, 2.36 updates/s | 1.49 | 1.84 |
| 120 (c 0.621, u 0.320, o 0.096 s) | 1.037 s, 0.96 updates/s | 0.717 s, 1.39 updates/s | 1.45 | 1.67 |

This assumes the update's threads do not take cores from the game workers; with U update threads competing on K cores add about (U/K)·u. Each run (segment) overlaps neither its first collection nor its last update: about min(c, u) per run, 0.2% of a 256-update run, 3% of a 16-update one. Memory: a net-8 parameter set is 4.9 MB (1.23 M parameters; 14.8 MB with moments), so the second set (β_j's policy and parameters in the update) is small. The real cost is coincidence: the next batch's collection working set (worker game states and policy clones, its published trajectories at about 2.7 MiB per game, 0.16 GiB at 60 and 0.32 GiB at 120 games, plus their parse-ahead copies) is live while the update holds its own batch's parsed trajectories, decoded tensors (256 MiB default bound) and tapes. Peak RSS becomes about the sum of the two phases' peaks instead of the larger; measure it at 60 and 120 games.

## Implementation (this change)

- Run config (`native_expanded_training_run_v1`): `collection_policy_lag_v1` (0 or 1, never serialized at 0) and `collection_policy_lag_carry_v1` (a continuation's carry, checked at run start against the initial checkpoint's record). `validate_v1` refuses the flag outside the plain CPU GAE update and a `completed_iteration` opponent less than two iterations old. The run loop computes each batch's behaviour from receipts (`lagged_behaviour_v1`), resolves `current` opponents to it, validates collections against it, and passes it to the update command. While update j runs on the run thread, a helper thread collects batch j+1 into an ordinary attempt of iteration j+1 (`start_next_collection_v1`); the iteration's receipt is published before the helper is joined, a helper failure is reported only if the run goes on to that batch, and dropping the handle waits for the helper, so no collector outlives the run or its lock. An iteration-limit stop starts no helper. The follow mode's continuation check requires the carry to be the previous result's `collection_policy_lag_next_behaviour_v1`.
- Update (`expanded_deck_training_v1`): `Update` and `UpdatePrepared` take `collection_policy_lag_v1: {behaviour}`. A behaviour other than the source must be the input the source checkpoint records, one Adam step earlier (`load_lagged_behaviour_v1`); trajectories are bound to it and replayed on it, and its parameters become the step's gradient point. The checkpoint and `update.json` record the lag.
- Learner (`native_policy_train_step_v1`, `gae_v1`): a one-step gradient point on the train state, taken by the GAE step: forward, bit check, loss and backward at the point, Adam on the state's own parameters and moments. Any other learner path refuses a set point.
- Every new member is absent without the flag, so today's commands, receipts, checkpoints and states keep their bytes.
