# Phase 1 cloud execution tools

Canonical source for offline payload packaging, exact artifact comparison, CPU workers, export/recovery and bounded leases. `baseline-provenance.json` records the byte-identical starting copy from the preserved experiment tools. Those original tools and all historical payloads/results remain unchanged.

Run these files as scripts, or add this directory to `PYTHONPATH`. The tools have no provider credentials embedded in their source. Packaging is offline and does not allocate a Pod. Campaign execution and paid allocation remain paused under the project instructions.

`pack.py` prepares ordinary training and frozen evaluation payloads. `pack_bo3.py` prepares a BO3 stream beginning with an ordinary checkpoint for every actor. Runtime build commit/archive pins identify the native binaries; payload helper pins independently identify these execution tools. Fresh initialization provenance retains the original manifest and parameter bytes even when descriptor paths move to Linux.

`prepare_volume.py` closes the network-volume gap next to `prepare_lease.py`, which only consumes a pre-existing `lease['network_volume_id']`. It builds an offline create-request template for one network volume in the EU-RO-1 data center `prepare_lease.py` targets, sized by default from the measured per-package payload plus recovery headroom and capped at 50 GB, with the API key represented by the same `__INJECT_AT_POST_DO_NOT_SAVE__` placeholder. Its `--verify` mode fetches and records only a volume's sanitized id, name, size and data center. Either live call requires `--execute`, an environment-held `RUNPOD_API_KEY`, and a funding snapshot no older than thirty minutes; the key is never printed or saved, and the receipt carries a storage cost note converted to the lease guard's per-hour line.

`prepare_lease.py --execute` performs the one live Pod-create POST from an already-`--spec`'d template, re-hashed before sending, key injected only in memory (`Authorization` header and the body's `env.RUNPOD_API_KEY`). It requires `RUNPOD_API_KEY`, a funding snapshot under thirty minutes old, and `--volume-id` matching the template's `networkVolumeId`. The image defaults to the pinned digest (`runtime_observation.IMAGE_REFERENCE`); a mutable tag needs `--allow-mutable-image`, checked again at `--execute` time. Success writes six sanitized fields to `created-pod.json`; a non-2xx or malformed response writes `create-pod-failure.json` and exits nonzero. Neither the raw response nor the key is ever saved.

`lifecycle_timing.py` assembles the `phase1-complete-work-timing/v1` envelope `throughput.qualify()` needs, from timestamped receipts (a JSON path, or a bare ISO-8601 timestamp for a stage with no receipt of its own). For `--environment cloud`: a funding snapshot, `created-volume.json`, `created-pod.json`, `guard.json`, `worker-start.json` plus `--worker-result` (or `--run-end`), the export receipt, and an independent release lookup showing `provider_absent: true`. For `--environment local`: `--input-preparation-start` plus the same staging/run/export markers, and a reason for each of `--allocation-not-applicable`, `--image-startup-not-applicable`, `--release-confirmation-not-applicable`. `--dry-run` validates and prints the envelope without writing anything.

`verify_pod_absent.py` performs the independent, read-only release lookup `lifecycle_timing.py --release-confirmed` and the runbook both want: a subsequent GET, not the guard's own in-process detection. Given `--pod-id` and `--execute`, it issues `--repeat` (default 2) consecutive `GET /pods/{podId}` lookups, `--interval` (default 30) seconds apart, and only calls the Pod absent when every one comes back not-found; a listing (Pod still returned) stops the loop early and records only its sanitized `desiredStatus`/`costPerHr`, and any 5xx, timeout, unexpected status or malformed body also stops the loop early but leaves `provider_absent` `null` with a `reason`, exiting nonzero so an ambiguous read can never be mistaken for confirmation. It writes `pod-absence-<podid>.json` under `--output-dir` with `observed_utc`, `pod_id`, `provider_absent`, the HTTP status observed, the endpoint used, the full per-attempt trail, and `key_saved: false`; that receipt's `provider_absent` and timezone-aware `observed_utc` fields already match what `lifecycle_timing.py --release-confirmed` reads, so it can be passed there directly. Requires `RUNPOD_API_KEY` in the environment only for `--execute`; without `--execute` it prints the GET it would make and touches no network.

Uploading to a Pod: `cloud_worker.py` cannot import without its full local-module closure, per its own imports (`cloud_worker.py` -> `runtime_observation`, `throughput` -> `semantic` -> `fresh_source`). Upload all six: `common.py`, `fresh_source.py`, `semantic.py`, `runtime_observation.py`, `throughput.py`, `cloud_worker.py`. A four-file list in a different repo's historical runbook misses `runtime_observation.py` and `fresh_source.py`. Later invocations reuse the payload's own bundled copy instead.

The lease, funding, numerical compatibility, throughput and release gates still apply. A passing offline test or local Linux replay does not qualify a paid RunPod burst. See [the fresh-origin design](../../../docs/PHASE1-FRESH-CLOUD.md) and [Phase 1 plan](../../../docs/phase1_pauper_meta_competence.md).

Focused suite, with temporary storage on a permitted volume:

```text
python -B -m unittest discover -s python/tools/phase1_cloud -p "test_*.py"
```

Tests marked for actual retained artifacts require the associated local evidence. Preserve their explicit skips when those files are unavailable. This suite does not execute the MTG native binaries or allocate cloud resources.
